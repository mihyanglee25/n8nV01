CHAPTER 01-03 · FLOW LOGIC

데이터 흐름의 이해

n8n의 핵심은 노드를 많이 아는 것이 아니라 JSON 데이터가 분기·병합·반복·대기·재사용·오류처리를 거쳐 어떻게 이동하는지 이해하는 데 있다.

01 개요01-01 비교01-02 용어01-03 흐름

1. Splitting: 데이터를 나누기

If 노드

조건이 참/거짓 두 경로일 때 사용한다.

Webhook → If(문의에 "긴급" 포함?) ├─ True → 관리자 즉시 알림 └─ False → 일반 처리 큐

Switch 노드

세 개 이상의 조건으로 분기할 때 적합하다.

주문 데이터 → Switch(금액) ├─ 소액 ├─ 중액 ├─ 대액 └─ VIP

Split Out 노드

한 아이템 안에 들어 있는 배열을 여러 개의 개별 아이템으로 분해한다.

  • 첨부파일 배열을 파일별로 저장한다.
  • 사용자 목록을 사람별 이메일 작업으로 분해한다.

2. Merging: 데이터를 합치기

모드개념간단 예
Append두 데이터 목록을 아래로 이어 붙인다.[A,B] + [C,D] → [A,B,C,D]
Merge by Fieldsid 같은 키를 기준으로 결합한다.{id:1,name} + {id:1,age}
Merge by Position같은 순서의 아이템끼리 결합한다.1번째↔1번째, 2번째↔2번째

예를 들어 API 사용자 정보와 DB 구매 이력을 id 기준으로 합치거나, 여러 지점의 매출 결과를 하나의 리포트로 묶을 수 있다.

3. Looping: 여러 아이템 반복 처리

Loop Over Items는 배열의 각 아이템을 순서 또는 배치 단위로 처리할 때 사용한다.

고객 100명 → Loop Over Items → 개인화 메시지 전송 ↑_______________________↓ 반복
  • 고객별 이메일 발송
  • 여러 파일 순차 업로드
  • API Rate Limit을 피하기 위한 천천히 요청

조건 기반 반복

If와 연결해 특정 상태가 될 때까지 다시 확인하는 폴링 패턴을 만들 수 있다. 무한 루프가 되지 않도록 최대 반복 횟수나 종료 조건을 반드시 둔다.

4. Waiting: 대기와 재개

대기 방식예
시간 기반30분 후 다음 단계 실행
특정 시각다음날 오전 9시까지 대기
Webhook관리자 승인 신호가 들어올 때까지 일시 중단
Send Email → Wait 30분 → Check Response
초보자 포인트
Wait는 단순히 프로그램을 멈추는 것이 아니라 “실행 상태를 저장하고 나중에 이어서 진행”하는 용도로 이해하면 쉽다.

5. Sub-workflow: 공통 로직 재사용

여러 Workflow에서 반복하는 로직을 별도 Workflow로 분리하고 Execute Workflow 계열 노드로 호출한다.

  • 고객 정보 검증
  • 이메일 템플릿 렌더링
  • 데이터 클렌징
Workflow A ─┐ ├→ 공통 데이터 검증 Sub-workflow → 결과 반환 Workflow B ─┘

코드의 함수처럼 공통 기능을 한 번만 관리할 수 있어 유지보수가 쉬워진다.

6. Error Handling: 실패를 설계한다

Error Workflow

실패 이벤트를 별도 Workflow에서 수신해 Slack·메일 등으로 알린다.

Continue On Fail

일부 아이템의 실패가 전체 처리를 멈추지 않게 한다.

Retry On Fail

일시적 네트워크나 DB 장애 때 지정 횟수와 간격으로 재시도한다.

Stop And Error

필수 데이터 누락 등 비정상 상황에서 의도적으로 실행을 중단한다.

HTTP Request ├─ 성공 → Process Response └─ 실패 → Retry 3회(5초 간격) → 여전히 실패 → Error Workflow

7. Execution Order: 실행 순서

화면상으로 두 브랜치가 나란히 보인다고 해서 항상 진정한 병렬 처리라는 뜻은 아니다. 일반적인 한 실행 내에서는 각 경로의 실행 순서와 Merge 도달 조건을 이해해야 한다.

Trigger ├─ Branch A ─┐ └─ Branch B ─┴→ Merge → Next
고부하 병렬 처리
수백·수천 건의 실제 분산 처리가 필요하다면 Queue mode, Redis, 여러 Worker, Sub-workflow 비동기 구조 등을 별도로 검토한다.

8. 실전 패턴 5가지

패턴 1 · 조건부 알림

Trigger → If → True: Alert / False: Log

패턴 2 · 데이터 통합 및 가공

Source A ─┐ ├→ Merge → Transform → Save DB Source B ─┘

패턴 3 · 재시도 가능한 API 호출

Trigger → HTTP Request(Retry 3, Wait 5s) → Process

패턴 4 · 승인 Workflow

Submit → Wait(Webhook) → If 승인? → Execute / Reject

패턴 5 · 복잡한 배열 처리

Get Data → Split Out → Loop Over Items → Process → Merge → Export

9. 초보자 종합 실습

“고객 문의 자동 분류” Workflow를 만든다고 가정한다.

  1. Webhook으로 문의 데이터를 받는다.
  2. If에서 “긴급” 여부를 판단한다.
  3. 긴급이면 Slack 관리자 채널로 보내고, 일반 문의는 DB 저장 경로로 보낸다.
  4. 첨부파일 배열은 Split Out으로 분리한다.
  5. 파일마다 Loop Over Items로 저장한다.
  6. 두 경로의 결과가 필요하면 Merge로 합친다.
  7. 외부 API 노드에는 Retry On Fail을 적용한다.
  8. 전체 실패는 Error Workflow로 알린다.
